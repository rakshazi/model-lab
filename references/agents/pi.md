# Pi as the test stand

Local models through Pi in the netless sandbox ([IISD-sandbox](https://github.com/rakshazi/IISD-sandbox), set up for Pi at `~/.pi/docker`). The lab procedure is in `SKILL.md`; this page is what Pi changes. Measured with a 27B writing an implementation plan through a skill that calls a reviewer subagent. Each bullet is the fact, then the run or the source line behind it. Re-probe after a Pi update: `trace.py SESSION --system` answers most of "What the model receives" in one call.

## Running a batch

```bash
for n in 1 2 3; do SKILL=<skill> LAB=/tmp/<skill>-lab ARGS='<the task as a user would type it>' MAXTIME=20m \
  bash scripts/pi/run.sh v1 $n llama-swap/qwen3.5-4b; done > /tmp/<skill>-lab/runs/v1.log 2>&1
```

- **The model id is the one `~/.pi/agent/models.json` gives it**; `llama-swap/qwen3.5-4b` and `llama-swap/qwen3.8-27b` are examples.
- **`ARGS` is what a user types after `/skill:<skill>`.** Pi expands the command itself, so the prompt needs no wrapper.
- **The skill is read from `~/.pi/agent/skills/<skill>`** and frozen at `~/.pi/lab/skills/VARIANT/SKILL/`. Pi wants `name:` to match the parent directory, so the snapshot keeps the skill's own directory name and reaches the run through `-ns --skill`.
- **Lean by default.** `-ne -ns -nc`, a blank append and Pi's four default tools. Each comes back through its knob: `EXT`, `CONTEXT=1`, `APPEND=1`, and `TOOLS` by name. An extension tool also needs its extension in `EXT`.
- **Pi has no `--max-time`.** `run.sh` starts a watchdog that, after `MAXTIME`, kills the container found by its workspace mount: `docker ps --filter volume=/home/agent/workspace/<cwd with / turned into ->`. The sandbox runs `docker run -it`, and with a TTY the docker client forwards no signals, so killing the client leaves the container alive. A 25 s limit on a task that sleeps 300 s ended as `exit=137 wall=33s timeout=1` with no container left; `result.txt` carries the `timeout=1`.
- **Sessions are keyed by variant and run number, with no lab in the path.** Two labs that reuse a variant name overwrite each other's `~/.pi/lab/sessions/<variant>/<n>/`, and `session.txt` in the earlier lab then points at a deleted file. Give each lab its own variant names (`a-old`, `b-old`), or read the session before the second lab runs.
- **`trace.py` and `summary.py` read Pi sessions unchanged.** Event shape, usage fields, `stopReason` and tool-call blocks match omp's. `run.sh` writes the session path to `session.txt`, and `summary.py` reads that before it falls back to the omp location.
- **A skill that names its script by installed path runs the live copy.** A skill that calls `~/.pi/agent/skills/<skill>/scripts/x.sh` executed that file while its body came from the snapshot. For such a skill the rule "the live skill can be edited while a batch runs" is false: wait for the batch.
- **An output outside the repo needs the lab hook.** A file the skill writes under `~/.pi/` is still there on the next run, which finds it and treats it as existing work. `assets/check-outside.example.sh` moves the files the run wrote into `RUN/outside/` before checking them.
- **Paths in the output are container paths.** A file written in the sandbox cites `/home/agent/workspace/-tmp-...-repo`. A host-side check has to resolve against `RUN/repo` and drop any state file that recorded the container path.
- **A subagent leaves no session of its own.** The `Agent` tool worked in print mode with `run_in_background: false`. The child's report sits in the parent session as a `subagents:record` custom event, its tokens are absent from the parent's usage, and its turns are invisible to `trace.py`: the wait shows up as long gaps (362 s inside a 510 s review). A subagent on a cloud model also means the run measures two models, so leave `Agent` out of `TOOLS` unless the subagent is part of what the skill is.
- **A first-move question needs no Pi loop.** To ask which tool a model reaches for under one prompt text or another, build the request from a real session's `system` event (the `sections` joined as the system message, `toolsAdded` as the function list), post it to the model server's `/v1/chat/completions` with one user message, and grade the `tool_calls` of the reply. Sixty such requests on a 4B took about two minutes, one thread per arm so each of its two slots keeps one arm's prefix, where a sandbox batch of three takes an hour and an `Agent` call would start a cloud run. It also reaches `ask_user_question`, which a print-mode run did not declare with the tool in `--tools` and its extension loaded. The first move was a fair proxy on the cell that mattered: replayed for a second turn with a canned tool result, no run that read the file first went on to delegate.

## What the model receives

- **The session file records it.** Every Pi session opens with a `system` event that holds the rendered system prompt by section (`preamble`, `tools`, `rules`, `docs`, `addendum`, `skills`, `cwd`) and the full schema of every declared tool. `python3 -I scripts/trace.py "$(cat $RUN/session.txt)" --system` prints one line per section and the tool names; `--has TEXT` names the sections and tool schemas that contain TEXT and exits 1 when none does. Run it on the first run of every setup. omp keeps no such record and has to ask the model, whose answer is the weak link: `references/agents/omp.md`, "Probing" (read when the same skill runs on both harnesses).
- **An extension that rewrites the request leaves the session file behind.** A `context_with_system` handler sent the `Agent` description at 704 characters while the session's `system` event kept all 6,432, and a `before_provider_request` rewrite behaved the same. With such an extension loaded, `trace.py --system` reports the text from before the rewrite. The probe is then a second extension, loaded last, whose `before_provider_request` handler only appends the payload's tool names, description lengths and system length to a file.
- **Print mode expands `/skill:NAME`.** The first user message of a `pi -p "/skill:NAME add an endpoint"` run was `<skill name="NAME" location=".../SKILL.md">`, a line `References are relative to DIR.`, the body with the frontmatter stripped, `</skill>`, a blank line, then the arguments. `run.sh` sends the command a user types and forges nothing.
- **`~/.pi/agent/APPEND_SYSTEM.md` rides in every session as `addendum`.** Whatever a user keeps there (a persona, house rules; 6K in the measured setup) reaches every run. An explicit `--append-system-prompt` replaces the discovered file instead of adding to it, so `run.sh` passes a blank one by default and the section arrives as an empty tag. `APPEND=1` keeps the file, for a run that should meet the skill the way a real session does.
- **`--system-prompt` replaces `preamble` alone,** 126 characters by default. The tool list, the rules, the docs pointer, the skills index and the cwd still arrive.
- **A lean run is small:** 2.3K of system prompt and four tools. The skill under test added a 1.5K skills index; an interactive session carried a 9.7K index for 13 skills.
- **Default tools are `read`, `bash`, `edit`, `write`.** `grep`, `find` and `ls` exist and are off. A skill that tells the model to search with a `grep` tool names something it does not have: write `rg` through `bash`, or add the tools through `TOOLS`. Plain names in `--tools` replace the whole selection, extension tools included, so every tool the skill needs has to be named.
- **`-ne` takes extension-registered providers with it.** With extensions off, a model that an extension supplies no longer resolves (`Warning: No models match pattern "<provider>/..."`), and a subagent pinned to it cannot start. Name the provider's extension in `EXT` next to the one that brings the tool.
- **`-nc` drops AGENTS.md and CLAUDE.md discovery** per the CLI reference. No run here had a context file present, so the flag is used and unproven.

## Extensions that call a model

- **A grammar goes per request through `samplingParams`.** `ctx.modelRegistry.streamSimple(model, context, { samplingParams: { grammar } })` merges the field into the body for OpenAI-compatible servers, so one served model handles a constrained caller and an unconstrained one (titles and compaction on the same 1.7B). The session-title prompt scored 118 of 251 usable replies bare and 243 with the grammar.
- **A TUI-only extension is tested through a pty.** `ctx.mode` is `print` under `-p`, and a subagent's child session binds with no mode and gets `print` too, so a `ctx.mode !== "tui"` gate covers both. The driver forks `just run` on a pty, answers the `ESC[c` and `ESC[6n` terminal queries, types the prompt, sends `\r`, and reads the `session_info` entry from the session file; `-na` skips the project trust question.
- **`before_agent_start` carries the prompt after expansion.** A `/skill:NAME args` arrives as the `<skill>` block; the exported `parseSkillBlock` returns the name and the arguments, and `pi.getCommands()` holds the description under `skill:NAME`.
